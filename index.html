SriniKai: a private, self-hosted LLM assistant

I wanted my own ChatGPT that never sends a single token to a third party. So I built the whole stack (a polished chat UI, a hardened API, retrieval memory, and tools) around a model that runs entirely on my own hardware via llama.cpp.

How it fits together

Frontend
static HTML · single file
Chat UI. Holds the JWT in localStorage and streams replies token-by-token. Never talks to the model directly.
HTTPS
SSE stream
SriniKai API
FastAPI · Python
The brain. Auth, rate limiting, context assembly, and the only path to the model; it injects the system prompt and trims history.
HTTP
stream
llama-server
llama.cpp · local
The model itself (Gemma weights) running on the host, exposing an OpenAI-style API. No cloud, no keys.
SQL store
SQLite (dev) · Postgres + pgvector (prod)
Users, conversations, messages, and embedded memories for retrieval.
Tools
web search · fetch · memory
Keyless web search + page fetch (with an SSRF guard) and long-term memory retrieval.
MCP server
Model Context Protocol
The same tools exposed over MCP, so Claude Desktop / IDEs can call them too.
the browser only ever talks to the API; the model server is never exposed

What happens in one chat turn

1
Authenticate & resolve
The request arrives with a Bearer JWT. Middleware checks CORS + per-IP rate limits, the token is verified, and the conversation is loaded, with ownership enforced by user_id.
2
Assemble context (RAG)
The message is embedded, then the top-k most relevant past memories are retrieved by cosine similarity and injected into the prompt. Optionally a live web search is folded in too.
3
Proxy to the model
System prompt + memory + trimmed history + the new message are sent to llama-server with stream=true. The proxy strips upstream model identifiers on the way out.
4
Stream & persist
Tokens stream straight back to the browser as Server-Sent Events; when the turn completes, the assistant reply is saved and the message is stored as a new long-term memory.

Built to be production-grade, not a toy

Real auth
Passwords hashed with argon2; JWTs signed with a secret. The app refuses to boot in production with a default secret.
SSRF-guarded web access
URL fetching blocks private, loopback and link-local targets, so the server can't be used as a proxy into the internal network.
Hardened edges
CORS allowlist, strict security headers on every response, rate limits, and generic errors that resist account enumeration.
Deploys for real
Dockerised stack (Postgres + pgvector, API, UI) with an AWS deployment guide; secrets via AWS Secrets Manager, never git.

Stack

llama.cppFastAPIPythonPostgrespgvectorSQLiteargon2JWTSSE streamingDockerAWSMCP

The takeaway: I can take an ML idea all the way to a secure, self-hosted product, with model serving, retrieval, a real API, auth, and deployment included.

FaRe-CPP: fast-revisit coverage path planning

How should a patrol robot move so that every part of a building is revisited as often as possible, as quickly as possible? I designed an algorithm that plans those patrol routes from a floor map, using the robot's long-range sensor so it covers more ground per stop. Lead-author work, published at IROS 2025.

How it fits together

Environment map
occupancy grid · .pgm / .yaml
A floor plan of the space as free / occupied cells, plus resolution and origin. The free area is measured up front.
feeds
FaRe-CPP planner
offline · Python + C++ port
The core. Picks where to stop, orders those stops into the best revisit route, and stitches them into a drivable path.
waypoints
Patrol execution
ROS · Gazebo · TurtleBot3
The optimized waypoints drive a robot patrolling the route in simulation (AWS RoboMaker / warehouse worlds).
Coverage goals
long-range sensor model
Sweeps the map and places viewpoints so the sensor's field of view covers the whole space in as few stops as possible.
Route optimization
greedy + 2-opt (TSP-style)
Orders the viewpoints into the shortest fast-revisit tour, accounting for turning cost, not just distance.
Path + metrics
A* on the grid
Connects stops with collision-free A* paths and reports revisit time from travel length and cumulative rotation.
the planner runs offline; only the final waypoints are handed to the robot

How one plan is built

1
Load the map
Read the occupancy grid (.pgm) and its metadata (.yaml), then estimate the total free area to cover.
2
Generate coverage goals
A frontier-style sweep places viewpoints using the robot's surveillance_range, so each stop sees as much new area as possible. Parallelized across processes for speed.
3
Optimize the revisit route
A greedy randomized construction plus 2-opt local search orders the viewpoints into a short, balanced patrol loop, weighting rotation as well as distance.
4
Build the path and score it
A* links the ordered stops into collision-free motion; revisit time is computed from linear travel and cumulative turning, with before/after plots.
5
Patrol
The saved waypoints feed a ROS + Gazebo simulation where a TurtleBot3 executes the patrol in realistic indoor worlds.

What makes it work

Fast-revisit objective
Optimizes for how often each area is revisited, not just total coverage, which is what actually matters for patrol and surveillance.
Long-range sensing
Uses the full sensor range when placing viewpoints, so the robot covers far more ground per stop than short-range coverage planners.
C++ port, 10-100x faster
A standalone C++ implementation of the offline planner removes the Python runtime for production-speed planning.
Validated in simulation
Tested in AWS RoboMaker and Dynamic Logistics Warehouse worlds; published and presented at IROS 2025, Hangzhou.

Stack

PythonNumPyC++A* search2-opt / TSPMultiprocessingROS NoeticGazeboTurtleBot3AWS RoboMaker

The takeaway: I can turn a research problem into a real algorithm, prove it in simulation, optimize it for speed in C++, and publish the result as lead author.

RoboBrain: classical control vs. reinforcement learning

Can a robot arm learn to pick and place as well as we can program it to? We built both: a classical controller with hand-derived kinematics, and an RL agent that taught itself the same task over 5000 episodes, bootstrapped by imitating the classical controller. Team project at Ostfalia University.

How it fits together

RL agent
policy network · staged learning
Learns the pick-and-place policy from observations and rewards, starting from imitation of the classical controller.
action / obs
reward
Gymnasium env
custom QarmEnv
Wraps the simulated arm in a standard RL interface: observations, rewards, resets, and collision signals.
topics
pub / sub
ROS2 + Gazebo
Humble · physics sim
The simulated 4-DOF arm with gripper. Publishes joint states, executes joint commands, detects collisions.
Classical controller
FK / IK · trajectory planning
Forward kinematics, gradient-descent inverse kinematics, and a pick → place → home state machine. The baseline to beat.
Demonstration data
imitation learning
Trajectories recorded from the classical controller are cleaned, analyzed, and used to pre-train the RL agent.
Staged curriculum
6 stages · reach → grab → drop
Training difficulty ramps up gradually: first reach without collisions, then tighter tolerances, then grasping and dropping.
same task, two brains: the classical controller generates the data that gives the RL agent its head start

How the agent learned

1
Solve it classically first
Model the arm's kinematics, derive IK via gradient descent over joint angles, and script the full pick-and-place cycle as the reliable baseline.
2
Collect demonstrations
Run the classical controller repeatedly and record joint states, poses, and outcomes as training data.
3
Wrap the sim as a Gym env
A custom Gymnasium environment bridges the RL loop to ROS2 and Gazebo: actions become joint commands, sensor topics become observations and rewards.
4
Train in stages
A six-stage curriculum: reach the target, survive collision detection, tighten accuracy with dynamic tolerance, then learn grabbing and dropping.
5
Compare at 5000 episodes
Track the agent from random flailing at episode 1 to purposeful reaching and manipulation, benchmarked against the classical controller.

What makes it interesting

Two paradigms, one task
A direct, honest comparison of hand-engineered control against learned control on identical hardware and scenarios.
Imitation bootstrapping
The classical controller isn't thrown away; it becomes the teacher, generating demonstrations that pre-train the RL policy.
Curriculum learning
Staged difficulty (reach → grab → drop) with dynamic tolerances keeps the reward signal learnable at every step.
Real team delivery
Built by four developers with a product owner (Prof. Dr.-Ing. Peter Engel) at Ostfalia University, SoSe 2024.

Stack

PythonReinforcement LearningGymnasiumROS2 HumbleGazeboForward / Inverse KinematicsSimulinkImitation Learning

The takeaway: I understand robot control from both ends, the math of kinematics and the training loop of RL, and how to combine them so each covers the other's weaknesses.

Issue Labeling Bot: ML-powered issue triage for GitHub

Triaging issues by hand is boring, so I taught a bot to do it. A GitHub App that catches every new issue the moment it's opened, predicts the right label with a text classifier, applies it, and politely asks the author to correct it if wrong, feeding those corrections back into training.

How it fits together

GitHub
issues · webhooks
A user opens an issue. GitHub fires a signed webhook event to the bot's public endpoint.
webhook
signed payload
Webhook API
aiohttp · async Python
Verifies the event signature (GH_SECRET), routes it, and orchestrates prediction and response.
predict
Classifier
scikit-learn · joblib
A text classification model predicts the label from the issue's title and body.
GitHub API response
gidgethub
The predicted label is applied and the bot comments asking the author for feedback.
Feedback loop
corrections → retraining
User-corrected labels flow back into the feature store, so the model improves with real usage.
CI/CD
GitHub Actions · Procfile
Push to main builds and deploys the service; the same platform hosts the code and runs the bot.
the bot labels its own training data: every correction from a user is a free labeled example

What happens on every new issue

1
Receive & verify
The webhook arrives at POST /; the payload signature is checked against the shared secret before anything is parsed.
2
Predict
Title and body are concatenated and passed to the scikit-learn pipeline, which returns the most likely label.
3
Act on GitHub
Via gidgethub, the label is applied to the issue and a friendly comment invites the author to correct it.
4
Learn
Corrections are collected as fresh labeled data, and the model is retrained, closing the MLOps loop.

Why it's more than a script

Full MLOps loop
Development, deployment, serving, and monitoring: the model lives in production and its data pipeline feeds itself.
Async by design
Built on aiohttp so webhook bursts don't block; each event is handled in its own async task.
Verified events
Every payload is authenticated with the webhook secret, so nobody can spoof issues into the pipeline.
Human in the loop
The bot asks for feedback instead of pretending to be perfect, turning users into annotators.

The takeaway: I can ship a model as a living product, served async in production, wired into a real platform, and improving from its own users. Code on GitHub.
