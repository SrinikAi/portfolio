SriniKai: a private, self-hosted LLM assistant

I wanted my own ChatGPT that never sends a single token to a third party. So I built the whole stack (a polished chat UI, a hardened API, retrieval memory, and tools) around a model that runs entirely on my own hardware via llama.cpp.

How it fits together

Frontend
static HTML · single file
Chat UI. Holds the JWT in localStorage and streams replies token-by-token. Never talks to the model directly.
HTTPS
SSE stream
SriniKai API
FastAPI · Python
The brain. Auth, rate limiting, context assembly, and the only path to the model; it injects the system prompt and trims history.
HTTP
stream
llama-server
llama.cpp · local
The model itself (Gemma weights) running on the host, exposing an OpenAI-style API. No cloud, no keys.
SQL store
SQLite (dev) · Postgres + pgvector (prod)
Users, conversations, messages, and embedded memories for retrieval.
Tools
web search · fetch · memory
Keyless web search + page fetch (with an SSRF guard) and long-term memory retrieval.
MCP server
Model Context Protocol
The same tools exposed over MCP, so Claude Desktop / IDEs can call them too.
the browser only ever talks to the API; the model server is never exposed

What happens in one chat turn

1
Authenticate & resolve
The request arrives with a Bearer JWT. Middleware checks CORS + per-IP rate limits, the token is verified, and the conversation is loaded, with ownership enforced by user_id.
2
Assemble context (RAG)
The message is embedded, then the top-k most relevant past memories are retrieved by cosine similarity and injected into the prompt. Optionally a live web search is folded in too.
3
Proxy to the model
System prompt + memory + trimmed history + the new message are sent to llama-server with stream=true. The proxy strips upstream model identifiers on the way out.
4
Stream & persist
Tokens stream straight back to the browser as Server-Sent Events; when the turn completes, the assistant reply is saved and the message is stored as a new long-term memory.

Built to be production-grade, not a toy

Real auth
Passwords hashed with argon2; JWTs signed with a secret. The app refuses to boot in production with a default secret.
SSRF-guarded web access
URL fetching blocks private, loopback and link-local targets, so the server can't be used as a proxy into the internal network.
Hardened edges
CORS allowlist, strict security headers on every response, rate limits, and generic errors that resist account enumeration.
Deploys for real
Dockerised stack (Postgres + pgvector, API, UI) with an AWS deployment guide; secrets via AWS Secrets Manager, never git.

Stack

The takeaway: I can take an ML idea all the way to a secure, self-hosted product, with model serving, retrieval, a real API, auth, and deployment included.

FaRe-CPP: fast-revisit coverage path planning

How should a patrol robot move so that every part of a building is revisited as often as possible, as quickly as possible? I designed an algorithm that plans those patrol routes from a floor map, using the robot's long-range sensor so it covers more ground per stop. Lead-author work, published at IROS 2025.

How it fits together

Environment map
occupancy grid · .pgm / .yaml
A floor plan of the space as free / occupied cells, plus resolution and origin. The free area is measured up front.
feeds
FaRe-CPP planner
offline · Python + C++ port
The core. Picks where to stop, orders those stops into the best revisit route, and stitches them into a drivable path.
waypoints
Patrol execution
ROS · Gazebo · TurtleBot3
The optimized waypoints drive a robot patrolling the route in simulation (AWS RoboMaker / warehouse worlds).
Coverage goals
long-range sensor model
Sweeps the map and places viewpoints so the sensor's field of view covers the whole space in as few stops as possible.
Route optimization
greedy + 2-opt (TSP-style)
Orders the viewpoints into the shortest fast-revisit tour, accounting for turning cost, not just distance.
Path + metrics
A* on the grid
Connects stops with collision-free A* paths and reports revisit time from travel length and cumulative rotation.
the planner runs offline; only the final waypoints are handed to the robot

How one plan is built

1
Load the map
Read the occupancy grid (.pgm) and its metadata (.yaml), then estimate the total free area to cover.
2
Generate coverage goals
A frontier-style sweep places viewpoints using the robot's surveillance_range, so each stop sees as much new area as possible. Parallelized across processes for speed.
3
Optimize the revisit route
A greedy randomized construction plus 2-opt local search orders the viewpoints into a short, balanced patrol loop, weighting rotation as well as distance.
4
Build the path and score it
A* links the ordered stops into collision-free motion; revisit time is computed from linear travel and cumulative turning, with before/after plots.
5
Patrol
The saved waypoints feed a ROS + Gazebo simulation where a TurtleBot3 executes the patrol in realistic indoor worlds.

What makes it work

Fast-revisit objective
Optimizes for how often each area is revisited, not just total coverage, which is what actually matters for patrol and surveillance.
Long-range sensing
Uses the full sensor range when placing viewpoints, so the robot covers far more ground per stop than short-range coverage planners.
C++ port, 10-100x faster
A standalone C++ implementation of the offline planner removes the Python runtime for production-speed planning.
Validated in simulation
Tested in AWS RoboMaker and Dynamic Logistics Warehouse worlds; published and presented at IROS 2025, Hangzhou.
